# ЛР2 — Характеризационные тесты и нормализация БД

## Изменения

Миграция `V2__normalize_customers_and_order_items.sql` переводит исходную V1
на нормализованную схему без изменения самой V1:

- `customers`: `id`, `full_name`, `address`, `phone`;
- `orders.customer_id` — обязательный внешний ключ на клиента;
- `order_items.product_id` — обязательный внешний ключ на товар;
- копии контактов в `orders` и имени/цены товара в `order_items` удалены;
- для обоих внешних ключей добавлены индексы.

Одинаковый клиент определяется полным совпадением имени, адреса и телефона,
включая отсутствующие контакты. `UNIQUE NULLS NOT DISTINCT` (PostgreSQL 16)
и `INSERT ... ON CONFLICT DO NOTHING` защищают от дубликатов при параллельных
заказах. Одинаковое имя при разных контактах не объединяет клиентов.

В исходной V1 позиции содержат только имя и цену, поэтому восстановить
оригинальный ID товара при дублях каталога невозможно. Миграция выбирает
минимальный ID среди товаров с совпадающими именем и ценой. Если совпадения
нет, добавляет товар из сохранённых данных позиции. Старые заказы, их статусы,
время создания, количества, отзывы и существующий каталог сохраняются.
После миграции имя и цена позиции читаются из связанного товара.

Добавлены JPA-сущность клиента, репозиторий и сервис переиспользования клиента.
Заказы сохраняются с новыми связями в прежней общей транзакции. Формат
`POST /orders` и `GET /orders` остаётся прежним.

## Проверки

`PricingCalculatorTest` фиксирует поведение расчёта, включая границы количества
и суммы, порядок скидок и купонов, неизвестные и регистрозависимые коды,
отрицательные значения и округление. Нулевое или отрицательное количество
сам калькулятор не запрещает; это по-прежнему проверяется при создании заказа.

`CustomerNormalizationTest` проверяет API на новой схеме, повторное использование
контактов без телефона, раздельные адреса и товары с одинаковым именем,
параллельное создание клиента, внешние ключи и отказ без записи при неверном товаре.

`NormalizationMigrationTest` поднимает V1 в отдельной тестовой схеме,
заполняет её старыми данными, применяет V2 и проверяет сохранность заказов,
времени создания, позиций, отзывов, дедупликацию клиентов и восстановление товаров.
Тестовая схема удаляется в `finally`.

Для полной проверки нужны Java 21, Maven и Docker:

```sh
mvn -B verify
python3 scripts/write_score.py
```

Критерии ЛР2 в `score.json`: `lab2_schema.passed` и `lab2_coverage.passed`
равны `true` — по 10 баллов, покрытие строк всего проекта не ниже 60%.
Дополнительно должны оставаться зелёными тесты поведения ЛР1.
Эталонные тесты и правила начисления баллов не менялись.
