# ЛР4 — N+1 и выделение модуля отзывов

## Загрузка заказов

Раньше `GET /orders` выбирал заказы, затем для каждого отдельно загружал позиции.
После нормализации отдельные запросы добавлялись и для клиентов/товаров.

Теперь `OrderQueryService` выполняет два запроса:

1. `OrderRepository.findAllWithCustomer` загружает заказы вместе с клиентами
   через `JOIN FETCH`.
2. `OrderItemRepository.findAllWithProducts` загружает позиции сразу всех
   выбранных заказов, также через `JOIN FETCH` получая товары.

Позиции группируются по ID заказа в памяти; запросов внутри цикла нет.
Для пустого списка выполняется только первый запрос. Заказы без позиций
сохраняются в ответе с пустым `items`. Заказы и позиции упорядочены по ID.

Контроллер обращается к сервису чтения, а не к репозиториям. Сервис в read-only
транзакции собирает `OrderView`: наружу не выходят JPA-сущности, сериализация
не запускает дополнительные запросы. JSON сохраняет прежние поля `id`,
`customerFullName`, `status`, `items` с `productName` и `quantity`.

## Граница модулей

Прямые зависимости `ReviewService` от `OrderRepository` и `OrderItemRepository`
заменены интерфейсом `contracts.PurchaseHistory`. Интерфейс передаёт только ID
товара, имя автора и логический результат; сущности и репозитории в контракт
не включены.

`OrderPurchaseHistory` реализует контракт внутри модуля заказов. Проверка
выбирает число позиций по конкретному товару и компонентам имени клиента
одним SQL-запросом вместо загрузки всех заказов/позиций.

Так прежняя точка взаимодействия постепенно заменена адаптером (Strangler Fig):
отзывы зависят от контракта, реализация заказов остаётся за ним. Сам модуль
заказов не зависит от реализации отзывов; контракт не зависит от обоих модулей.

Как и в исходном API, отзыв разрешён без покупки. Результат проверки используется
для диагностической записи без контактных данных, а не для нового запрета.
API принимает свободное имя автора, поэтому совпадение имени не является
аутентификацией пользователя и не превращено в публичный признак верификации.

## Проверки

- `OrderListQueryTest`: 1, 10 и 50 заказов с разными клиентами и тремя отдельными
  товарами на заказ — ровно два SQL-запроса, все данные на месте. Для пустого
  списка — один запрос; отдельно проверен заказ без позиций.
- `ReviewServiceTest`: подмена только контракта покупки, сохранение отзывов
  с покупкой и без неё, анонимный автор и чтение без обращения к заказам.
- `ReviewIntegrationTest`: точное совпадение товара и имени, один SQL-запрос
  проверки покупки, отсутствие запроса для пустых входных данных, прежний
  формат HTTP API отзывов.
- `ModuleBoundaryTest`: контракт не тянет внутренности модулей, адаптер заказов
  не зависит от реализации отзывов.
- Неизменённые эталонные `NPlusOneReferenceTest` и `ArchitectureRulesTest`
  проверяют оба критерия ЛР4; тесты предыдущих работ продолжают запускаться.

Полная проверка (Java 21, Maven, Docker):

```sh
mvn -B verify
python3 scripts/write_score.py
```

Критерии ЛР4: `lab4_nplusone.passed` и `lab4_architecture.passed` равны `true`
в `score.json`, по 10 баллов. Миграции и правила оценивания не менялись.
