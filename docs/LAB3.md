# ЛР3 — Эволюция имени клиента без остановки приложения

## Этапы

1. `V3__lab3_expand_customer_names.sql`: добавляет `first_name` и `last_name`,
   оставляет `full_name`, включает двустороннюю синхронизацию триггером.
   Старый код по-прежнему пишет только `full_name`; новый код пишет новые поля,
   а триггер заполняет старое поле в той же транзакции.
2. `V4__lab3_backfill_customer_names.sql`: заполняет новые поля существующих
   клиентов через тот же триггер, вводит `NOT NULL` и уникальность сочетания
   имени и контактов с учётом `NULL` в необязательных контактах.
3. Приложение переводится на новые поля: `Customer`, `CustomerRepository`
   и `CustomerService` больше не обращаются к `full_name` в БД.
4. `V5__lab3_contract_drop_full_name.sql`: удаляет переходный триггер,
   функцию и старое поле. Новый уникальный ключ и все связи заказов сохраняются.

Старые миграции V1/V2, эталонные тесты и правила оценки не изменялись.

## Как выполнять переход при работающих экземплярах

Не запускать contract, пока хотя бы один экземпляр приложения использует
`full_name`. Для постепенного обновления сначала ограничить Flyway версией 4:

```sh
mvn spring-boot:run -Dspring-boot.run.arguments=--spring.flyway.target=4
```

При запуске новой версии накатываются expand/backfill; старые экземпляры
продолжают работать с прежним полем. Затем перевести все экземпляры на новый
код с тем же ограничением. Когда старых экземпляров больше нет, убрать
ограничение `spring.flyway.target` и применить V5 обычным запуском новой версии.
Работающие экземпляры нового кода совместимы и с V4, и с V5.

При первом запуске пустой учебной базы можно применить сразу всю цепочку.
Миграции берут обычные блокировки PostgreSQL на время изменения схемы;
нагрузочный тест проверяет, что запросы укладываются в заданный таймаут.

## Правило разделения имени

Имя делится по первому внутреннему пробелу: первая часть — `first_name`,
остаток — `last_name`. Для одного компонента `last_name` равен пустой строке.
Если пробел только в начале или конце, имя сохраняется целиком в `first_name`.
Повторные пробелы, дополнительные компоненты и исходное форматирование
не теряются. Из свободной строки нельзя надёжно угадать порядок имени и фамилии,
поэтому миграция не пытается переставлять компоненты.

Java-код `CustomerName` и SQL-триггер используют одинаковое правило.
API сохраняет поле `customerFullName`, собирая его из новых колонок;
клиентам API менять запросы не нужно.

## Проверки

- `CustomerNameTest`: разделение и обратная сборка, составные имена, один
  компонент, начальные, конечные и повторные пробелы.
- `NameMigrationLoadTest`: старый клиент непрерывно читает и вставляет
  `full_name`, пока применяются V3/V4; затем проверяются backfill, обновления
  обоих форматов и сохранность уникальности после V5.
- Второй сценарий `NameMigrationLoadTest` запускает настоящее приложение на V4.
  Три параллельных клиента читают `GET /orders` и создают заказы через
  `POST /orders` во время применения V5. Запросы имеют таймаут 5 секунд;
  проверяются успешные обращения каждого клиента до и после миграции,
  отсутствие HTTP-ошибок и таймаутов, сохранность данных и удаление колонки.
- Эталонный `LoadDuringMigrationReferenceTest` отдельно проверяет чтение старой
  колонки при expand/backfill и итоговую схему после contract.
- Проверки ЛР1 и ЛР2 должны продолжать проходить на окончательной схеме.

Полная проверка (Java 21, Maven, Docker):

```sh
mvn -B verify
python3 scripts/write_score.py
```

Критерий: `gates.lab3_migration.passed` равен `true` — 15 баллов.
